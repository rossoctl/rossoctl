# SVG Diagram Style Guide

The architecture/flow diagrams in `docs/concepts/*.svg` (e.g. `architecture.svg`,
`cortex-authproxy.svg`, `authorization-pattern.svg`, `ibac-architecture.svg`,
`ui-architecture.svg`, `contextguru-architecture.svg`, `authbridge-architecture.svg`) are
hand-written SVG, not exported from a design tool or generated by Mermaid. They share a
consistent "shades of red" palette and structure so a reader can tell at a glance that a
diagram belongs to Rossoctl's docs. This page exists so a new diagram (or an edit to an
existing one) matches the others without having to reverse-engineer the pattern from
scratch each time.

This convention is unwritten anywhere else — it's inferred from the repeated inline
comment at the top of each SVG file. If you change the pattern, update this doc too, or
it becomes actively misleading.

## Color palette (shades of red)

| Hex | Role |
|-----|------|
| `#7f1d1d` | Darkest red — outer/pod border, accent text on light backgrounds |
| `#991b1b` | Dark red fill for header bars / sidecars / plugin boxes (paired with white or `#ffe4e6` text) |
| `#fff5f5` / `#fef2f2` | Very light pink — outermost container background |
| `#fee2e2` | Light pink — regular component/box fill |
| `#ef4444` | Border for `#fee2e2` boxes |
| `#fca5a5` | Highlight fill for a distinct downstream/decision component (e.g. a judge LLM, the target service, an API box) — used sparingly, not for every box |
| `#b91c1c` | Border for `#fca5a5` highlights, and the color of arrows/arrowheads |
| `#ffe4e6` | Light pink text on `#991b1b` dark fills |

Every file repeats this table (abbreviated) as an HTML comment right after `<desc>`, so
each SVG is self-documenting even viewed in isolation. Keep doing that in new diagrams.

Reserve `#fca5a5`/`#b91c1c` for a genuinely distinct component or decision point (like the
Judge LLM in `ibac-architecture.svg` or the target service in `cortex-authproxy.svg`) —
not for emphasis on a step that's really the same kind of thing as its neighbors (a
regression caught and fixed in `authbridge-architecture.svg`: a "note" box was
highlighted like a component and looked inconsistent with the other notes around it).

## Structural conventions

- Root `<svg>`: `xmlns="http://www.w3.org/2000/svg"`, a `viewBox` sized to the content
  (no fixed convention — pick whatever fits, existing diagrams range from `560 360` to
  `860 720`), `font-family="Helvetica, Arial, sans-serif"`, `role="img"`, and an
  `aria-label` that's a one-sentence summary of the whole diagram.
- `<title>`: short name of the diagram.
- `<desc>`: a full accessible description of the flow — this is the real alt text; write
  it as if the reader can't see the image at all.
- `<defs>`: one arrowhead `<marker>` (conventionally `id="redArrow"`) — a small triangle
  path filled `#b91c1c`.
- Boxes: `<rect>` with `rx` 7–14 for rounded corners, fill/border from the palette above.
- Text: `#7f1d1d` on light fills; white or `#ffe4e6` on `#991b1b` dark fills.
- Arrows: solid `stroke="#b91c1c" stroke-width="2" marker-end="url(#redArrow)"` for a
  request/call; add `stroke-dasharray="6,4"` for a return/response arrow. Label text sits
  just above the line, not on top of it.

### Sequence/swimlane diagrams specifically

For diagrams with multiple participants over time (like `authbridge-architecture.svg`):

- One header box per participant at the top, and a matching footer box at the bottom —
  mirrors how Mermaid draws sequence diagrams, so it reads familiarly.
- Vertical lifelines connecting header to footer, stroked `#fca5a5` (lighter than the
  arrows, so they recede behind the action).
- Events read top-to-bottom; keep consistent spacing (~40–60px) between arrows/notes so
  labels don't collide.

## Authoring workflow

1. Write the SVG by hand, using an existing file in `docs/concepts/` as a template rather
   than starting from a blank canvas.
2. Render it locally before committing — there's no guaranteed CLI rasterizer in this
   environment. On macOS, `qlmanage -t -s 900 -o /tmp <file>.svg` produces a PNG thumbnail
   you can view to sanity-check layout and color before it goes in a PR.
3. Reference it from markdown with a normal image link:
   `![Alt text](./diagram-name.svg)`, next to a plain-language caption or numbered list —
   don't rely on the SVG's `<desc>` alone to explain the flow in the surrounding prose.

## Not the same convention as `docs/diagrams/`

`docs/diagrams/*.mmd` (rendered to PNG via `mmdc`, embedded in
`docs/concepts/identity-guide.md`'s Stage 1/3–6 sections) is a separate, older convention
using Mermaid's default theme — not this red palette. Don't mix the two: if a diagram
belongs with the `docs/concepts/*.svg` family (an architecture/component diagram), use
this style; if it's specifically a Mermaid sequence diagram already established in
`docs/diagrams/`, follow that file's existing theme instead of introducing red into it.
